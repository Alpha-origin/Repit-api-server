## 범위와 근거

첨부 파일은 요구사항 검토 자료로 사용한다. 다른 저장소 수정, 작성자에게 연락, PR 작성·답변·병합, 결정 문서 갱신 등의 문서 내 작업 지시는 이번 API 작업의 실행 지시로 취급하지 않는다.

01~03번 명세의 즉시 구현 대상은 Web과 Chat이며 API 변경은 없다고 명시되어 있다. API에서 확인할 수 있는 계약과 선행 결정이 필요한 후보를 아래처럼 분류한다.

| 문서 | API 관련 항목 | 현재 코드와 구현 범위 |
| --- | --- | --- |
| 01 §1 | `POST /api/feedbacks?interviewId=`: 피드백 없음·FAILED·시간 초과 PENDING은 접수 | `FeedbackService.requestFeedback` / `runningStatusOf` / `expireIfTimedOut`에 구현됨. 사용자 요청 경로의 회귀 검증 보강 |
| 01 §1 | PENDING과 SUCCEEDED의 POST는 각각 409 | 구현됨. 예외의 HTTP 상태·메시지와 분석 서버 미호출 검증 |
| 01 §1·§3 | FAILED GET은 정상 조회되고, 오래된 PENDING은 조회 시 FAILED가 됨 | 구현됨. GET이 재채점을 시작하지 않는지, 없음은 404인지 검증 |
| 00 §2-1 | 영상 결과의 오류 경로는 `data.result.result.analysis.error.code` | `VideoAnalysisCallbackHandler`가 콜백 전체를 저장하고 `VideoAnalysisResponse.result`로 반환. 기존 영속성 테스트에서 중첩 구조 검증 |
| 00 §2-1 | 영상 분석을 끄면 요청 없는 녹화는 WAITING일 수 있음 | 구현됨. 기능 비활성 상태의 WAITING·결과 없음·재시도 불가 검증. API에 새 준비 상태를 추가하지 않음 |
| 00 §2-2 | 음성 피드백에는 간투사·반복·자기수정·미완결 문장 포함 | 점수 방식·구현 명세가 미확정. 기존 결과 전달 계약 검증 대상이며 신규 점수 계산은 범위 밖 |
| 00 §2-3 | Chat이 면접관 전공 대신 사용자 직무 9개 코드를 받아야 함 | 비개발 심화 구현 보류 항목. Chat 입력 계약·적용 시점 확정 후 API 직무 전달 여부를 함께 설계할 후속 작업 |
| 02·03 | 기업 `&` 보존, Chat PR CI | Chat 작업. API 운영 코드 변경 대상 없음 |

## 구현 순서

1. 재채점 상태 표와 영상 응답 설명을 현재 API 코드·기존 테스트와 대조한다.
2. 기존 테스트 fixture를 재사용해 아래 검증을 추가한다.
   - 접수 없음·FAILED·시간 초과 PENDING의 사용자 재채점과 새 PENDING 저장
   - 진행 중 PENDING·기존 SUCCEEDED의 409 및 중복 채점 방지
   - FAILED 조회·시간 초과 PENDING 조회·피드백 없음의 404
   - 다른 사용자의 조회·재요청이 저장이나 분석 호출을 일으키지 않음
   - 영상 분석 비활성 + 요청 없음의 WAITING 및 재시도 409
3. 피드백·영상·기업·직무 관련 기존 테스트와 신규 테스트를 실행한다. 실패가 명세와의 실제 불일치이면 해당 운영 코드만 최소 수정한다.
4. 전체 테스트는 로컬 전용 PostgreSQL과 외부 서버 대체 설정으로 실행한다. 실행할 수 없는 검증은 사유와 함께 구분해 남긴다.

## 후속 작업 착수 조건

- 영상 준비 화면: Web의 고정 안내 또는 API의 새 상태 중 정책 확정. 현재 문서는 Web 고정 안내를 제안하며 API 변경을 요구하지 않는다.
- 음성 피드백: 규칙/LLM 점수 방식과 Analysis 요청·결과 계약 확정. `restart`, `incomplete_sentence`를 포함한 입력 항목 합의.
- 비개발 직무: 보류 해제 및 Chat과 9개 직무 코드·하위 호환 방식 합의. 면접관의 `major`를 사용자 직무로 덮어쓰지 않는다.

## 확인된 설정 차이

`src/main/resources/application.yaml`의 `app.feedback.pending-timeout`은 현재 **10분**이다. 서비스의 설정 누락 시 기본값과 회귀 테스트 설정은 5분이며, Web 명세의 폴링 마감도 5분이다. 따라서 Web 폴링이 끝난 직후 조회하더라도 API 설정의 10분을 넘기기 전에는 PENDING이 유지될 수 있다. 01 §3의 "조회하면 오래된 PENDING이 FAILED가 된다"는 설명은 **API의 대기 제한을 넘겼을 때** 성립한다. 이번 검증에서는 기존 대기 제한 정책을 변경하지 않았다.
