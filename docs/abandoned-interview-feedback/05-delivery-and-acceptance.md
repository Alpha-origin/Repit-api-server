# 05. 전달·호환 적용·인수 기준

상태: 구현 설계안. 아래는 **향후 구현·검증·적용 절차**이며 실행 기록이 아니다. 이번 작업은 서비스 코드 수정·테스트·데이터 변경·배포를 포함하지 않는다. 기존 인계의 배포 보류 결정을 유지한다.

## 1. 전달 범위와 담당

README를 포함한 7개 파일을 함께 전달한다. 구현 전 각 담당자는 공통 계약을 읽고 해당 저장소를 fetch하여 기준 커밋 차이를 확인한다.

| 담당 | 구현 범위 | 다른 담당과의 접점 |
|---|---|---|
| API | 실행·저장·조회·대기 작업의 최종 자격 통제 | Chat result 멱등성, Analysis 상태 선언, Web 409 |
| Chat | 조기 완료 방지·최종 상태·중단 outbox | API 상태 형식, Web END status |
| Analysis v2 | SOLO/MULTI 접수 전 필수 상태 검증 | API 필드 선전송 확인 |
| Web | 기존 완료 전용 UI 유지·종료/재시도 경합 | Chat 실제 최종 status, API 정책 응답 |

구 Analysis·Auth·Config 신규 구현은 없다. 구현이 명세와 달라져야 하면 먼저 문서를 고치고 영향받는 계약을 함께 갱신한다. 문서 PR 병합은 기능 구현·적용 완료를 의미하지 않는다.

## 2. 호환 적용 순서

### 2.1 사전 조사

- 실제 실행 저장소·버전·DB schema·모든 API/Chat 인스턴스를 확인한다.
- 이전 Chat outbox에서 종료 status 누락/null/IN_PROGRESS payload 건수와 복구 근거를 확인한다.
- ABANDONED의 dispatch WAITING·SENDING, Feedback/Audio/Video PENDING, 과거 성공 결과 건수를 읽기 전용으로 확인한다.
- 원본 기록·질문 PK·파일 보존과 완료 면접의 기존 동작을 비교할 기준을 확보한다.

### 2.2 호환성과 정책 적용

1. **Chat 생산자 보강:** 신규 종료 payload의 명시 status와 조기 COMPLETE 방지, 모든 END의 status를 준비한다. 중단 outbox는 유지한다. 과거 불명 payload는 근거를 확인해 별도 정리하며 신규 요청 허용 규칙을 느슨하게 만들지 않는다.
2. **API 최종 집행:** 실행·조회·콜백·복구·미디어 모든 경로를 차단한다. `interviewStatus`를 모든 텍스트 요청에 포함한다. result 형식 강화는 Chat 생산자와 이전 outbox 점검 후 적용한다.
3. **DB와 기존 대기 정리:** SKIPPED를 이해하는 코드·스키마의 호환 순서를 맞춘 뒤 조건부 배치로 정리한다. 보호 코드와 정리 사이에도 새 분석이 나가지 않아야 한다.
4. **Web 보완:** 새 END status를 소비하고 구 END 확인 절차·409·녹화 경합을 처리한다. API 보호의 적용을 Web 일정에 의존시키지 않는다.
5. **Analysis 필수화:** 모든 API 인스턴스의 자동·수동·재시도에서 필드 전송을 확인한 뒤 엄격 검증을 적용한다.

위는 호환 적용 설계다. 로컬 실연동 검증을 먼저 하고, 실제 배포·데이터 정리 실행은 별도 작업 지시가 있어야 한다. 전환 중 모든 구 인스턴스가 제거되기 전에는 전체 차단 완료로 표시하지 않는다.

### 2.3 되돌리기 제약

- Analysis 엄격화 이후 상태 필드를 보내지 않는 구 API로 단독 복귀하지 않는다. 호환되는 버전 쌍을 유지한다.
- DB에 SKIPPED가 기록된 후 해당 enum을 모르는 구 API 인스턴스를 실행하지 않는다. 데이터를 WAITING으로 되돌려 분석을 재개하는 방식으로 복구하지 않는다.
- 중단 결과를 다시 노출하는 보호 제거를 일반 복구 절차로 삼지 않는다. 완료 면접 회귀 문제가 생기면 정책 보호를 유지하며 원인을 수정한다.

## 3. 이전 데이터·대기 작업 정리 설계

[가정] 읽기 전용 집계 → 대상 ID 확정 → 소량 배치 조건부 갱신 → 잔여 집계·감사의 순서로 수행한다. 배치 크기·실행 시간은 실제 건수·잠금 영향을 확인해 실행 계획에 적는다. 이번 문서에 실행 가능한 일괄 UPDATE를 넣지 않는다.

| 대상 | 처리 | 보존·제외 기준 |
|---|---|---|
| ABANDONED dispatch WAITING·만료 SENDING | SKIPPED, 사유 INTERVIEW_ABANDONED | findDue·claim·retry에서 제외 |
| 활성 SENDING | 보호 코드로 외부 요청/결과 반영 차단, 만료 후 정리 | 강제 claim 탈취 금지 |
| ABANDONED Feedback/Audio/Video PENDING | 기존 FAILED + 정책 사유 | 일반 장애·자동 재분석 대상에서 제외 |
| 과거 ABANDONED 성공 결과 | 삭제 없이 보존 | 단건 조회 409, 목록·비교·카드 제외 |
| IN_PROGRESS 녹화·대기 | 보관·보류 | 완료 후 실행 가능, 영구 SKIPPED 금지 |
| 상태 불명 Chat outbox | 원 세션·확정 종료 근거 조사 | 답변 개수로 완료 추정 금지 |

마이그레이션 번호는 API 구현 직전 실제 최신 다음 번호를 쓴다(문서 기준 최신 V38). enum/check 제약, 늦은 워커의 상태·claim 조건, 배치 중 동시 콜백을 함께 검토한다. 분석·피드백 데이터만 정리하고 면접·질문·답변·파일을 정책 차단 때문에 삭제하지 않는다.

기존에 원격 접수된 분석은 실제 모델 실행이 계속될 수 있다. 이 대상은 신규 ABANDONED 분석 요청 0회 측정과 분리하여, **추가 재전송 0회·늦은 결과 저장/노출 0회**로 검증한다.

## 4. 통합 인수 시나리오

각 상태 시나리오를 SOLO/MULTI × TEXT/VOICE × 기업 없음/있음에 적용한다. 미디어 기능이 꺼진 환경의 호출 0회만으로 기능이 켜진 경로의 차단을 통과 처리하지 않는다. 원격 client 대역과 DB 검증을 사용하고 유료 모델 실호출은 별도 승인 없이는 하지 않는다.

| ID | 상황·입력 | 기대 결과 |
|---|---|---|
| A01 | 답변 0개·일부 답변 후 QUIT | ABANDONED 기록 2xx, 기존 질문·답변 보존, 신규 텍스트/기업/음성/영상 요청 0회 |
| A02 | 마지막 질문까지 정상 진행 | COMPLETED, 기존 피드백·기업 코멘트·미디어 분석 허용 |
| A03 | 질문 남은 상태의 REST/WS COMPLETE | 완료 전이·outbox 생성 없음, 기존 진행 가능 |
| A04 | COMPLETE↔QUIT, 마지막 ANSWER↔QUIT 경합 | 먼저 확정한 종료 상태 유지, 반대 중복에도 질문 PK 보존 |
| A05 | 신규 result status 누락/null/IN_PROGRESS | 422, 기록 claim·dispatch·외부 요청 없음 |
| A06 | ABANDONED/IN_PROGRESS 수동 생성·재시도·미디어 재분석 | 소유권 검증 뒤 409, 외부 요청·새 분석 행 없음 |
| A07 | ABANDONED WAITING·만료 SENDING sweep 반복 | SKIPPED 유지, 오류 backoff·재전송 증가 없음 |
| A08 | SKIPPED 뒤 오래된 워커 markDone/scheduleRetry | 상태 부활·재claim 없음 |
| A09 | 녹화 선업로드 후 COMPLETED | 저장 성공, 완료 이후 기존 유예·기능 정책으로 실행 |
| A10 | 녹화 선업로드 후 ABANDONED | 저장 성공, sweep·get 복구에도 분석 0회 |
| A11 | 중단 작업의 늦은 성공/실패·조기 콜백 | 식별·권한 검증, 알려진 작업 2xx, 행·항목·companyFit 생성/갱신 없음 |
| A12 | 중단 음성의 미확인 접수 재전송·영상 조회 복구 | 원격 재전송·새 결과 저장·자동 재분석 없음 |
| A13 | 과거 중단 성공 결과의 단건·목록·비교·URL 직접 진입 | 단건 409, 목록·결과 카드·기업 코멘트 제외 |
| A14 | Analysis 상태 누락/null/불허 값, 나머지는 유효 | SOLO/MULTI 422, UUID/task/LLM/companyFit/콜백 0회 |
| A15 | Analysis COMPLETED 요청 | 기존 202·jobId·채점·성공/실패 콜백 유지 |
| A16 | API 장애 중 QUIT, 이후 재시작·outbox 재전송 | 중단 payload 유지, API 저장 후 SENT, 분석 0회 |
| A17 | END 신규 status·구 END·404·늦은 QUIT 응답 | 확정 상태에 맞는 화면, 미확인을 완료로 추정하지 않음 |
| A18 | 409 후 Web polling·재시도·늦은 성공 응답 | polling 중지, 생성 재호출·결과 카드 부활 없음 |
| A19 | disconnect·새로고침·브라우저 강제 종료 | 임의 COMPLETED 없음, 완료 전 분석 미실행 |
| A20 | 비소유자·잘못된 내부 호출·미확인 콜백 | 기존 인증·식별 오류 유지, 정책 생략으로 우회 불가 |

완료 면접의 질문/답변 부족·기존 실패 처리, 조기 정상 콜백 복구, 중복 콜백, 정상 재채점, 미디어 기능 설정·재시도 제한도 회귀 기준에 포함한다.

## 5. 완료 증빙

- 네 저장소의 구현 커밋·리뷰 결과·로컬 검증 환경을 기록한다.
- API/Chat `./gradlew test`, Analysis `uv run ruff check && uv run mypy src && uv run pytest`, Web `npm run lint && npm run build`를 구현 완료 후 수행한다.
- API claim·최종 상태 경합은 실제 DB persistence 검증을 포함한다.
- 신규 중단 면접 ID별 외부 client 호출 수 0, 신규 피드백/분석 행 0, 기록 보존을 함께 증빙한다.
- 과거 작업은 정리 전후 건수와 늦은 콜백 저장/노출 0을 별도 증빙한다.
- 정책 생략과 실제 장애·차단 outbox를 구분하여 정책 생략이 장애 재시도로 반복 집계되지 않는지 확인한다.

문서 작성 완료, 구현 완료, 로컬 인수 완료, 실제 적용 완료를 각각 구분한다. 이번 PR이 충족하는 단계는 문서 작성과 문서 자체 검토까지다.
